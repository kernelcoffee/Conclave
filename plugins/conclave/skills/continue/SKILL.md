Use after a pause, after a session ended mid-task, or to pick one of several open tasks.
argument-hint: "[slug]"

Resume a task the Conclave lead paused or lost. Read `${CLAUDE_PLUGIN_ROOT}/agents/lead.md` first: you act as the lead from the stage you resume, following its per-stage procedure, pacing rules and commit proposal.

Arguments: `$ARGUMENTS` (an optional run slug).

## Steps

1. Read `.claude/conclave.json`. Read `.claude/conclave/runs/*.json`. A run is open when its plan document's Status is not `done` or `stopped`.
   - No slug and exactly one open run: use it.
   - No slug and several open runs: list them (slug, task, stage done, plan document path, last update) in one table and stop; the user picks one and calls `/conclave:continue <slug>`.
   - No open run: say so and stop.
   - A slug with no run JSON but a plan document under `docs.plans` that matches it: say that the stage state is lost (the JSON was deleted, or, in a project that commits its plans, the run came from another machine) and offer to restart from the document, taking the tier from its Tier line. The document must be present on this machine: plan documents are not committed by default, so a run started on another machine cannot be restarted here unless its document was committed or copied over. A document whose Status is `planning` has not been approved: it restarts through the `planning` rules in step 2 (at T2 and T3 the analysis checkpoint first when its step is present and unticked and `plan` is unticked, then the approval gate), and `build` is never offered from it; the run JSON's `plan_only` key is lost with it, so a plan-only run restarts at the tier of its Tier line. A document at `approved` or later restarts from its briefs: a T2 at `build` with `exec.brief` taken from the Briefs section, and a T3 at `plan` unless the user says the briefs are final, in which case at `build` with those briefs as `state.briefs`. Wait for the answer.
2. Read the run JSON (`task`, `slug`, `plan_doc`, `tier`, `exec`, `stage_done`, `state`) and the plan document. The next stage is the one after `stage_done`: `null` → `analysis` (T3, or a plan-only run: `plan_only: true` in the run JSON) or `build` (T2 with `exec.brief`), `analysis` → the analysis checkpoint, then `plan`, `plan-team` (a plan-only run whose specs `conclave:plan-team` wrote) → while the document's Status is `planning`, the approval gate, then `plan` with `conclave:dev-team`; once it is `approved` (the approval was given and the dev-team `plan` stage stopped or was cut off before it saved), straight to `plan` with `conclave:dev-team` on the saved `state`, as the approval bullet below describes, without asking for approval again (at T1, your own build from the Briefs), `plan` → `build`, `build` → `review`, `review` → `finish`, `finish` → the commit proposal. A run whose document Status is `planning` (for example one written by `/conclave:plan`) has not been approved:
   - At T2 outside a plan-only run, when the Steps list holds the `analysis checkpoint` step unticked and `plan` unticked, resume at the analysis checkpoint in `lead.md`, not at the approval gate: write the Analysis if it still holds the template's placeholders, show its summary and Unknowns, each with what would settle it and your recommendation, and wait for the user's confirmation; then write the specs and go on to the approval gate.
   - At T3 or in a plan-only run, when the `analysis checkpoint` step is unticked and `plan` is unticked: with `stage_done: null` and no `state.analysis`, launch stage `analysis` with the saved `state`, then hold the checkpoint as `lead.md` says for T3; with `stage_done: "analysis"`, or with a `state.analysis` already saved (an Analysis the lead wrote before a re-triage raised the task to T3), hold the checkpoint on it, without a new `analysis` launch (write the Analysis from `state.analysis` first if the section still holds the template's placeholders). Never write a spec before the user confirms.
   - At T3 or in a plan-only run, when the step is ticked with any outcome, or the document has no such step, and `plan` is unticked: the run is past the checkpoint; re-read the Analysis section into `state.analysis` and launch `plan` as `lead.md` says, without `exec.proceed` and without `exec.decisions` (drop both from the saved `exec`: a correction the `analysis` stage carried is already in `state.analysis`, and the plan stage would read it as answers to its own questions). A document with no Analysis section, or one whose Analysis holds only the template's placeholders or the one-line note an earlier version wrote in place of an analysis, gives no `state.analysis`: remove any saved one and pass none, so the plan stage runs the architect's analysis before the pm instead of specifying on an empty reading. A plan-only run is launched with `conclave:plan-team`, as the plan skill describes, and stops at the approval gate.
   - Otherwise (the step is ticked with any outcome, and documents written by an earlier version may read `skipped`; or `plan` is ticked, so the plan stage already wrote the specs and they are never rewritten; or the tier is T1 outside a plan-only run, where the checkpoint is part of the approval gate; or the document has no such step because it was written before the step existed and is treated as past the checkpoint): at T1 and T2 write whatever still holds the template's placeholders, the Analysis first at T1 (at T3 and in a plan-only run the specs come from the `plan` stage), then show the summary the approval gate in `lead.md` describes, and wait for the user's approval.
   - On approval tick the steps the approval gate ticks, set Status `approved`, and only then launch `build` (in a plan-only run, the `plan` stage first, as below). Never launch `build` from `planning`. A plan-only run saved with `stage_done: "plan-team"`, just approved or found at `approved`, goes on with `conclave:dev-team` from the `state` the plan skill saved, with the `exec` `lead.md` builds for the tier of its Tier line and `brief: ""`: first stage `plan`, which re-runs neither the analysis, nor the pm, nor the architect because that `state` holds a `plan`, and runs only the design duel and the consults the `exec` and the plan call for; then `build`. At T1 you build it yourself from the Briefs, as `lead.md` says for T1.
3. Re-read the Briefs section of the plan document and copy each `#### <component>` body (under Technical spec, Briefs) into `state.briefs[<component>]`; at T2 outside a plan-only run, while the saved `state` is null or holds no `plan`, into `exec.brief` instead (the T2 build synthesises its plan from `exec.brief` only when the state holds none; once a stage returned a state with a `plan`, `review` and `finish` read the briefs from `state.briefs`). Before a `plan` launch, also re-read the Analysis section into `state.analysis`, each subsection into the field of the same name, unless step 2 says the document gives none. Say in one line whether the briefs or the Analysis changed since the last stage. Pass `state` otherwise unchanged.
4. Run the preflight from `lead.md` for the branch and the tree (the branch in the document must be the current one; a dirty tree is reported, not stashed).
5. Print the triage line from the document, the next stage and its estimated agents, then launch it with `exec.stage` and `exec.state` as `lead.md` describes, and continue the per-stage procedure: update the document, save the run JSON, pause when the pace says so.

Write nothing to the repository other than the plan document and the run JSON until the stage returns.
