# FastAPI stack pack

Load together with `stack-python`. Covers FastAPI routers, dependency injection, pydantic
v2 schemas, SQLAlchemy 2.x async (or SQLModel), Alembic, WebSockets and background work
with APScheduler or asyncio tasks.

## Idioms

- Layering: a router validates input, calls a service and shapes the response; business
  logic in services; every database access through a repository or a clearly named data
  layer; models separate from API schemas; external systems behind thin clients.
- One pydantic schema per request body and per response (`response_model` declared and
  accurate); no raw dicts returned; a single error shape produced by exception handlers,
  not re-implemented per router.
- Status codes exact: 201 on create, 204 on empty success, 400 invalid input, 401/403 for
  auth, 404 missing, 409 state conflict, 422 only for schema validation, 429 when an
  upstream rate-limits.
- Dependencies: sessions and services from one `dependencies` module; a request-scoped
  session is never pinned for the life of a WebSocket or a worker; workers open their own
  short sessions.
- SQLAlchemy 2.x: `Mapped[...]` declarations, `select()` with explicit loading options
  (no lazy loads in async code), commit before broadcasting or responding, refresh after
  commit when the row is returned, no detached instance read after the session closes.
- Migrations: Alembic with `render_as_batch=True` on SQLite; added columns nullable or
  defaulted; a migration file is reviewed, not just autogenerated; an applied revision is
  never edited. Projects without Alembic use an add-column-only reconciliation and must
  never rename, drop or retype.
- Datetimes UTC, serialised with the `Z` suffix, produced by one helper.
- WebSockets: register on accept, unregister in `finally`, broadcasts drop dead clients,
  bounded queue per client, payloads JSON-serialisable; a broadcast failure never breaks
  the action it reports.
- APScheduler: stable job ids with `replace_existing=True`, `max_instances` respected,
  started on the running loop, pause and resume through one service, state persisted,
  job errors recorded and broadcast rather than propagated into the request that
  scheduled them.
- App factory with a lifespan handler that initialises the DB, scheduler and reconciliation,
  and shuts them down cleanly.

## Review checklist

- A router reaching a session, a repository or an external client directly.
- Missing or wrong `response_model`; a status code that does not match the outcome; an
  error raised as a bare `HTTPException` where a domain exception and handler exist.
- A pydantic schema that accepts more than it should (no `extra = "forbid"` on strict
  inputs, unbounded strings or lists, no range on numbers).
- Session lifecycle: a session held across an await on an external call, two sessions
  writing the same row in one request, a commit missing before the response, a lazy
  load in async code (`MissingGreenlet`).
- A model change without a migration; a non-nullable column added to an existing table; a
  downgrade that does not undo the upgrade; batch mode missing on SQLite.
- A sync endpoint introduced, or an async endpoint that blocks the loop.
- WebSocket handlers without cleanup, unbounded fan-out, a broadcast that can raise into
  the caller.
- Scheduler jobs added twice, not removed on pause or disable, overlapping with a manual
  trigger, left running after shutdown; persisted state disagreeing with the live scheduler.
- Path confinement on every file-serving or file-writing endpoint: absolute paths, `..`,
  symlinks pointing out, zip-slip on extraction.
- Request bodies and uploads without a size cap; list endpoints without pagination or a cap.
- Secrets or session tokens reaching a log line, an error `details` payload, a WebSocket
  event or a response they did not already appear in.
- OpenAPI summary and description present like the neighbours.

## Testing

- `httpx.AsyncClient` with `ASGITransport` (or the project's `test_client` fixture) against
  the app with an in-memory or temp-file database from `conftest.py`; one engine per test
  or a transaction rolled back per test.
- Assert status code and body shape, then the side effect (row written, file created,
  event recorded, job scheduled). A test that only checks a 200 proves little.
- Every expected failure from the brief as a test: rejected inputs with their status and
  error code, state conflicts, missing resources, confinement violations.
- External clients through `httpx.MockTransport` with recorded fixtures; the scheduler
  patched to run jobs on demand; WebSockets tested through the test client's `websocket_connect`.
- Migration tests: when a column is added, a test that creates a database at the previous
  state and upgrades it.

## Tooling

- Dev server: `uvicorn <package>.main:app --reload`; checks: `ruff check .`,
  `python -m pytest -q`; coverage: `--cov=<package> --cov-report=xml`.
- Alembic: `alembic revision --autogenerate -m "<change>"` then review the file;
  `alembic upgrade head`; `alembic stamp head` only for a database created before
  migrations existed.
- Swagger at `/docs` and ReDoc at `/redoc` when the server runs; use them to confirm a
  contract, not the code comments.

## Pitfalls

- `Depends()` in a signature flagged by a linter and then suppressed instead of configured
  (B008 is normally ignored for FastAPI).
- A session fixture that commits between tests and leaks rows.
- Background tasks started with `asyncio.create_task` and dropped; their exceptions vanish.
- `datetime.utcnow()` (naive) mixed with aware values from the database.
- A WebSocket broadcast loop that awaits a slow client and stalls everyone.
- Returning ORM objects directly, exposing columns the schema did not intend.
- Pydantic v1 patterns (`class Config`, `.dict()`) in a v2 project; use `model_config`
  and `.model_dump()`.
